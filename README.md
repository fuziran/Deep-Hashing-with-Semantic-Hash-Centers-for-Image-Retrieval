# Deep Hashing with Semantic Hash Centers for Image Retrieval

## Overview
This repository is the PyTorch implementation of ACM TOIS 2025 (CCF A) paper: "Deep Hashing with Semantic Hash Centers for Image Retrieval".

![structure](./save_figures/structure.png)

**SHC** is a three-stage framework designed to generate hash codes that accurately preserve semantic information, significantly enhancing large-scale image retrieval performance.

### Core Workflow
<ol>
  <li><strong>Semantic Similarity Detection</strong>: Construct a classification network to identify semantic relationships between classes, and adopt a data-dependent similarity calculation method that flexibly adapts to different data distribution characteristics.</li>
  <li><strong>Semantic Hash Center Generation</strong>: Propose a new optimization algorithm that maintains the semantic relevance of hash centers while ensuring a minimum distance between them through distance constraints. This effectively addresses the issue of degraded retrieval performance caused by excessively close hash centers.</li>
  <li><strong>Deep Hashing Network Training</strong>: Train a deep hashing network based on the generated semantic hash centers to efficiently convert images into binary hash codes.</li>
</ol>


### Experimental Results
Experiments on large-scale image retrieval across several public datasets demonstrate that the hash codes generated by SHC have stronger discriminative power, significantly improving retrieval accuracy and efficiency.​
Feel free to explore the implementation details in the code repository or conduct secondary development based on this framework!

## Getting Started
1. Clone this repository:
```
git clone https://Deep-Hashing-with-Semantic-Hash-Centers-for-Image-Retrieval.git
cd Deep-Hashing-with-Semantic-Hash-Centers-for-Image-Retrieval
```

2. Create a conda environment and install the dependencies:
```
conda create -n SHC python=3.10.0
conda activate SHC
pip install torch==2.1.2 torchvision==0.16.2 torchaudio==2.1.0 --index-url https://download.pytorch.org/whl/cu121
```

## Code Introduction
- `GenerateSimilarityMatrix.py` is stage1 in SHC, you can easily use it to generate SimilarityMatrix on your own dataset.
- `GenerateSemanticHashCenters.py` is stage2 in SHC, you can generate SemanticHashCenters based on SimilarityMatrix.
- `network.py` contains all the networks used in SHC, including classification network and hash network. The default is ResNet34. If you need to modify the backbone, you can do so here.

## Train

### Audited B0 baseline (CIFAR-100)

The main B0 protocol reserves 10 images per class from the 10,000-image
training pool for validation. The 5,000-image query set is used only once for
the final evaluation. Run the CPU-only unit tests before using the GPU:

```bash
python3 -m unittest discover -s tests -v
```

Run a one-epoch smoke test first:

```bash
export CUBLAS_WORKSPACE_CONFIG=:4096:8
python3 run.py --dataset cifar-100-new-seg \
  --root ./data/cifar-100-python \
  --num-classes 100 --code-length 32 --seed 60 \
  --classify-epoch 1 --epoch 1 --test-map 1 \
  --batch-size 64 --num-workers 4 --topK -1 100 1000
```

For the reported B0 result, restore both epoch counts to 300. Splits, cache
metadata, the selected checkpoint, all three mAP values, per-query AP and
binary codes are written under `save/`. Use `--stage similarity` or
`--stage centers` to stop after a diagnostic stage, and use
`--force-recompute` only when intentionally replacing a matching cache.

### Audited B0 baseline (NABirds-B)

Use the curated NABirds-B archive, with `train/`, `query/`, and `database/`
directories under `images/`. The training directory must contain 555 class
subdirectories; query classes must have matching training and database classes.
The loader uses these existing splits; it never resamples the
paper's B split from raw NABirds. It reserves two images per class from `train/`
for validation, using `--seed 60`. The validation images are excluded from
training and from the retrieval database. The query set is evaluated only after
the best Stage 3 checkpoint has been chosen on validation mAP@ALL.

From the repository root on the GPU machine, set `NABIRDS_ROOT` to the extracted
archive's `images` directory. The commands below run all three code lengths in
separate run directories and leave the CIFAR-100 outputs untouched:

```bash
export CUBLAS_WORKSPACE_CONFIG=:4096:8
NABIRDS_ROOT=/absolute/path/to/NABirds-B/images
for bits in 16 32 64; do
  python3 run.py --dataset NABirds-B --root "$NABIRDS_ROOT" \
    --num-classes 555 --code-length "$bits" --seed 60 \
    --lr 1e-4 --classify-epoch 300 --epoch 300 --test-map 5 \
    --beta 1.0 --lambd 1e-4 --batch-size 64 --num-workers 4 \
    --resize-size 256 --crop-size 224 --val-per-class 2 \
    --topK -1 100 1000 --gpu 0 --output-dir ./save_nabirds_b
done
```

The loader writes the sorted class mapping, relative image paths, split
indices, counts, and split SHA256 under `save_nabirds_b/splits/`. Check the
printed counts against the extracted archive before committing to a long run.
The PDF reports 16,384 train, 8,171 query, and 25,612 database images, but
those counts do not sum to the 48,562 images it reports for the official A
split. This code records the actual supplied B archive counts instead of
silently changing its splits. After reserving validation, Stage 3 reports
`mAP@ALL`, `mAP@100`, and `mAP@1000` in each run's `metrics.json`.

The PDF uses a `1e-4` learning rate for non-CIFAR datasets, 300 epochs in
Stages 1 and 3, batch size 64, and quantization weight `1e-4`. The fixed
validation holdout and checkpoint selection follow this repository's audited
B0 protocol and may differ from the paper's exact evaluation procedure.

### Reliability-guided B1 on NABirds-B

This branch also supports `--variant b1` for NABirds-B. B1 uses only the
training portion of the curated split to estimate a two-view, reliability-
weighted class relation and visual-feature relation. Their fused matrix
replaces B0's Stage 1 matrix; Stage 2 and Stage 3 keep the same center and
hash-network objectives. The classifier cache is shared by B0 and B1 when
their training configuration matches, while the relation and center caches
remain separate. B1 diagnostics are saved in `stage1_diagnostics.pt`.

For a paired comparison, use the same code version, split, seed, and options
for both variants, including `--paired-stage-seeds`. The flag resets the hash
network initialization and training order after center generation. Retain
`--val-per-class 2` for NABirds-B. Use a new output directory to keep the
earlier B0 runs intact; their previous scores are useful context but are not
the paired B0 result under this flag and code revision.

The CIFAR-100 default of `--relation-kappa 30` is preserved here as a fixed
starting configuration. NABirds-B has fewer training images per class, so
inspect the saved effective class counts and fusion gates before interpreting
the relation mechanism. Select checkpoints on validation mAP@ALL and use the
query set only for final reporting.
